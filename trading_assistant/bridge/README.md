# TradingView → Telegram

Мост на Python 3.10+ без сторонних зависимостей. Он принимает структурированные события стратегии, сохраняет их в SQLite и отправляет уведомления отдельным потоком. HTTP-обработчик не ждёт Telegram: после сохранения возвращает `202`, чтобы уложиться в трёхсекундный лимит TradingView.

Это уведомления стратегии и её симулятора. Мост не открывает позиции на бирже и не подтверждает реальное исполнение ордеров. Цены приходят из Pine; AI их не придумывает.

## Запуск

Из корня репозитория:

```bash
export WEBHOOK_SECRET="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
python -m trading_assistant.bridge --port 8080 --database /tmp/trading-assistant.sqlite3
```

Без настроек Telegram сервер сохраняет события и очередь, но ничего не отправляет. Для доставки задайте **в окружении процесса** `TELEGRAM_BOT_TOKEN` от BotFather и `TELEGRAM_CHAT_ID` своего чата; оба значения обязательны вместе. Пользователь должен предварительно открыть бота и нажать Start. Перезапустите процесс с тем же файлом базы.

Файл `.env.example` показывает названия параметров. Автоматической загрузки `.env` нет. Не сохраняйте настоящие секреты в Git, Pine-коде, опубликованных скриптах или скриншотах. `WEBHOOK_SECRET` длиной минимум 24 символа также задаётся в соответствующем закрытом поле настроек TradingView-скрипта.

Другие параметры окружения:

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `MAX_EVENT_AGE_SECONDS` | `300` | Старше этого окна события записываются как подавленные |
| `MAX_STATE_AGE_SECONDS` | `5400` | Свежесть часового состояния в `/state` — отдельно от доставки сигналов |
| `SEND_CONTEXT` | `false` | Уведомлять об изменениях контекста |
| `SEND_BREAKOUT` | `false` | Уведомлять о пробое до ретеста |
| `ENABLE_COMMANDS` | `true` | Включить Telegram-команды по последним снимкам Pine |

По умолчанию в Telegram приходят подготовка входа, достижение условия входа, отмена и выход. Контекст и пробой обновляют состояние без сообщений.

После настройки Telegram доступны команды:

- `/btc` — последний наблюдаемый сценарий BTC/USD, BTC/USDT или BTC/USDC;
- `/eth` — аналогичный сценарий ETH;
- `/status` — состояния до десяти наблюдаемых инструментов.

Ассистент отвечает только в `TELEGRAM_CHAT_ID` из окружения; для команд нужен числовой ID личного чата. Другие чаты и сообщения ботов игнорируются. Ответы содержат тренд, этап, плановые уровни подготовленной/активной модели, срок ожидания и дату снимка по Москве. Устаревшие данные и истёкшее ожидание отмечаются явно. Если данных ещё нет, бот предлагает подключить TradingView. Котировки не запрашиваются, свободные вопросы и AI в этой версии не используются.

Команды получают сообщения через Telegram `getUpdates` отдельным потоком; HTTP webhook TradingView продолжает работать независимо. Один Telegram-бот должен иметь только одного потребителя `getUpdates`: отключите другие polling-процессы и существующий Telegram webhook для этого бота либо установите `ENABLE_COMMANDS=false`. База хранит update-offset; после перезапуска уже обработанные команды не отвечаются повторно. Ответ подтверждается после отправки, поэтому при сбое между доставкой и сохранением offset возможен повтор ответа. Постоянный отказ Telegram в отправке ответа пропускает эту команду, чтобы не блокировать последующие; сетевые ошибки и ограничения частоты повторяются. Это команды просмотра: торговых действий на бирже они не выполняют.

Сервер слушает `127.0.0.1:8080`. Для TradingView нужен постоянный публичный HTTPS-адрес на порту 443 через обратный прокси с сертификатом, например Caddy или nginx. Прокси должен ограничивать размер тела запросов и частоту обращений. Не отправляйте секрет через обычный HTTP. TradingView требует включённую двухфакторную аутентификацию для webhook-алертов и принимает webhook-порты 80/443. Этот локальный запуск сам по себе не публикует адрес в интернете.

## API

`POST /webhook` принимает JSON от стратегии:

```json
{
  "schema_version": 1,
  "strategy": "trend_retest_v1",
  "secret": "YOUR_PRIVATE_WEBHOOK_SECRET",
  "event_id": "BINANCE:BTCUSDT|setup-1|setup",
  "setup_id": "BINANCE:BTCUSDT|setup-1",
  "sequence": 12,
  "event": "setup",
  "stage": "armed",
  "symbol": "BINANCE:BTCUSDT",
  "timeframe": "60",
  "direction": "long",
  "trend": "bullish",
  "event_time": 1800000000000,
  "bar_time": 1799996400000,
  "entry": 100000,
  "stop": 99500,
  "target": 101000,
  "rr": 2,
  "risk_pct": 0.5,
  "expires_at": 1800003600000,
  "reason": "Ретест подтверждён; ждём пробой максимума свечи"
}
```

Цены и даты в примере условные; для запроса замените timestamps актуальными значениями миллисекунд Unix. Допустимые события: `context`, `breakout`, `setup`, `trigger`, `cancel`, `exit`. Соответствующие стадии: любая допустимая стадия для контекста; `waiting_retest`, `armed`, `active`, `canceled`, `closed` для остальных. Полный список стадий также включает `idle`. Направления: `long`, `short`, `none`; тренд: `bullish`, `bearish`, `neutral`. До подготовки плана ценовые поля и `rr` могут быть `null`, а `risk_pct` — `0`; для стадий `armed`/`active` все торговые уровни и положительный риск обязательны. `expires_at` может быть `null`: активная позиция не наследует срок ожидания входа.

Секрет сравнивается через `hmac.compare_digest` и не записывается в базу. Неизвестные поля, повторённые JSON-ключи, нечисловые или бесконечные цены и противоречивые SL/entry/TP отклоняются. `expires_at` ограничен семью днями после события; стратегия использует более короткое ожидание. Максимум тела — 16 KiB. Ошибки формата возвращают `400`, неверный секрет — `401`, превышение размера — `413`, недоступная база — `503`.

Успешный HTTP-ответ: `{"status":"accepted"}` или `duplicate`. Запоздавшие, просроченные, пришедшие в обратном порядке или пытающиеся повторно активировать закрытый сценарий события получают `suppressed_late`, `suppressed_expired`, `suppressed_order`, `suppressed_closed`. Эти ответы тоже имеют код `202`: событие сохранено, но уведомление не отправляется и текущее состояние не меняется.

`event_id` сохраняется между повторами доставки. Повтор не создаёт вторую запись очереди. Изменение существенных полей при том же ID возвращает `400`. События упорядочиваются по `event_time`, затем `sequence`, отдельно для каждого символа. `sequence` может сброситься после перезапуска Pine, если новый `event_time` больше предыдущего. Не меняйте timestamp при повторной отправке исходного webhook.

`GET /health` доступен без секрета: состояние сервера, включён ли Telegram, числа `pending`, `sent`, `failed`, `suppressed` в очереди. Секреты и тела событий не возвращаются.

`GET /state?symbol=BINANCE%3ABTCUSDT` требует заголовок `X-Webhook-Secret: ...`. Возвращает `state`, `age_seconds`, `stale`. Для неизвестного инструмента — `404`. Это основа будущей команды ассистента «Что сейчас по BTC?». Контекст должен содержать полный снимок текущего сценария: этап, его ID и уровни, если он подготовлен или активен. `stale=true` означает отсутствие обновления дольше `MAX_STATE_AGE_SECONDS` (по умолчанию 1,5 часа) либо истечение `expires_at` ожидающего ретеста/входа. Это оценка свежести состояния, а не мониторинг подключения к TradingView. Пятиминутное окно `MAX_EVENT_AGE_SECONDS` отдельно ограничивает своевременность торговых уведомлений: часовой сценарий не устаревает через пять минут после закрытия свечи.

## Очередь и доставка

SQLite сохраняет события, текущие состояния и очередь одной транзакцией; WAL и `synchronous=FULL` используются для сохранности. Один процесс обслуживает одну базу. Telegram-вызов выполняется за пределами HTTP-обработчика и SQLite-транзакции.

Перед отправкой проверяются срок ожидания, возраст и актуальность сценария. Задержанное сообщение «вход подготовлен» подавляется, если сценарий уже активирован, отменён или заменён. Подготовка и активация входа не отправляются позже `MAX_EVENT_AGE_SECONDS` после события, даже если они вовремя поступили в очередь: после длительного сбоя Telegram старые входы не объявляются актуальными. Отмены и выходы остаются информационными и могут доставляться позднее.

На `429` используется `retry_after`; сетевые ошибки и `5xx` повторяются с задержкой. Постоянные `4xx` помечаются `failed`; такие события видны в `/health` и требуют исправления настройки и ручного разбора очереди. При выключенном Telegram очереди сохраняются. После сбоя процесса забранная задача снова станет доступна в течение 60 секунд.

Гарантируется дедупликация входящих webhook по ID. У Telegram нет ключа идемпотентности: при потере ответа после фактической отправки или сбое до отметки `sent` возможно повторное сообщение. Весь HTTP-трафик и сырые ошибки Telegram не журналируются, чтобы не раскрывать секреты. Следите за `/health` и размером базы; автоматического удаления истории в первой версии нет.

## Проверка

```bash
python -m unittest trading_assistant.bridge.test_bridge trading_assistant.bridge.test_commands -v
```

Тесты проверяют авторизацию, формат и уровни, нечисловые значения, повторную доставку после перезапуска, порядок событий, отмену, срок входа, HTML-экранирование, быстрый HTTP-ответ и повторы после `429`. Команды проверяются на чужой чат, отсутствие данных, свежесть/срок ожидания, выбор последнего сценария и сохранение offset после перезапуска. Реальные сообщения Telegram не отправляются.
